# Day 1 — Rules: диффы двух генераций

Задача-датчик: `GET /api/scheduler/jobs` (список задач планировщика: `task_id, task_type,
next_run, interval_seconds`). Каждая генерация — свежий изолированный субагент с чистым
контекстом; единственная управляемая переменная — версия `CLAUDE.md` на диске.

- `CLAUDE.v1.md` — исходные правила (150 строк): только стек/запуск/деплой, про стиль кода **ничего**.
- `CLAUDE.v2.md` — правила v2 (259 строк): + naming, паттерны, инвариант «reuse-first»,
  6 примеров хорошего кода, 6 антипаттернов, шаблон модуля.

## Раунд 1 — промпт с жёсткой структурой (я продиктовал файлы вывода)

Промпт требовал отдельно `scheduler_store_fn.py` + `scheduler_endpoint.py` + тест.

Итог: `gen1` и `gen2` **идентичны по коду** (отличаются только докстринги). Оба написали
**новую** `list_scheduler_jobs()`, хотя в `app/scheduler_store.py:114` уже есть `list_jobs()`.

Вывод раунда: когда промпт сам диктует структуру решения, правила не могут повлиять на
архитектурный выбор — я его уже сделал за модель. Плюс стиль (`from __future__`, докстринги,
типы) `gen1` скопировал у соседних файлов даром — правилам негде было прибавить.

Артефакты: `gen1/`, `gen2/`.

## Раунд 2 — нейтральный промпт (свобода выбора реализации)

Промпт: «реши сам, как лучше реализовать в рамках существующего кода».

| Критерий | fair_v1 (правила v1) | fair_v2 (правила v2) |
|---|---|---|
| Переиспользовал `list_jobs()` | ✅ да | ✅ да |
| Тронул `scheduler_store.py` | нет (правильно) | нет (правильно) |
| Разделение слоёв (роут не лезет в SQLite) | ✅ | ✅ |
| Публичный контракт полей | хардкод инлайн | **вынес в константу `_JOB_PUBLIC_FIELDS`** |
| Детерминизм ответа | без сортировки | **`sorted(key=next_run)`** |
| tool_uses (сколько исследовал) | 9 | 11 |

Артефакты: `fair_v1/`, `fair_v2/`.

Ключевая разница fair_v2 — вынесенная константа `_JOB_PUBLIC_FIELDS` и детерминированная
сортировка. И то, и другое прямо следует из добавленных в v2 правил
(«константы — в модуль, не хардкодь по месту»; акцент на контракте).

## Честные оговорки по методу

1. **n=1 на условие — это шум.** LLM имеет разброс между запусками. Разница между
   `gen1` (не переиспользовал) и `fair_v1` (переиспользовал) объясняется не версией правил,
   а свободой промпта + случайной разницей в глубине исследования. Для строгого замера нужно
   3–5 прогонов на условие и смотреть на долю «правильных».
2. **Чистая кодовая база маскирует эффект правил.** Там, где рядом есть эталонный сосед,
   модель имитирует его без правил. Правила сильнее всего там, где эталона нет (greenfield)
   или где наивный дефолт расходится с домашним стилем.
