# Day 10 — Micro-model first: проверка перед LLM

**Дата:** 2026-07-31. Челлендж advance, неделя 8.

Задача: входящее обращение в поддержку нужно разложить по интентам — деньги, поломка, доступ,
потеря данных, отзыв, «не к нам». В Дне 7 это делала большая модель: каждое обращение, включая
«Не могу войти, пароль не подходит», стоило вызова `gpt-4.1` — а с гейтом уверенности и вовсе
трёх сэмплов. Между тем половина потока — это шаблонные фразы, которые уже сто раз приходили в
поддержку почти дословно. Для них большая модель не нужна: достаточно вспомнить, куда отнесли
похожее обращение в прошлый раз.

День про то, чтобы поставить перед LLM дешёвый уровень и честно замерить, сколько он отсекает и
чем за это платим.

## Задача

**Вход:** текст обращения в поддержку.
**Выход:** метка интента из enum — тот же список, что у триажа Дня 7 (`MICRO_LABELS = TRIAGE_CATEGORIES`):

| Метка | Что это |
|---|---|
| `billing` | оплата, списания, счета и акты, тарифы, возвраты |
| `technical` | продукт не работает: ошибки, падения, тормоза, API |
| `account` | вход, пароль, коды, права, приглашения, удаление аккаунта |
| `data_loss` | данные пропали или испортились, нужен откат |
| `feedback` | отзывы, благодарности, идеи, жалобы без запроса действия |
| `other` | не про поддержку продукта: сотрудничество, вакансии, пресса |

## Уровень 1 — micro-model

Никакой LLM: метка берётся из банка размеченных примеров (8 штук на класс,
[`data/micro_bank.jsonl`](../../data/micro_bank.jsonl)) по ближайшим соседям. Два взаимозаменяемых
бэкенда:

- **`embed`** — kNN по эмбеддингам (`openai/text-embedding-3-small` через RouterAI). Векторы банка
  считаются один раз и лежат в `data/micro_cache/`; на запрос уходит один дешёвый вызов
  `/v1/embeddings` — на порядки дешевле вызова `gpt-4.1`. Работает и с локальной Ollama:
  `RAG_EMBEDDINGS_URL=http://localhost:11434/v1/embeddings`, `RAG_EMBEDDING_MODEL=bge-m3`.
- **`tfidf`** — символьные n-граммы (3–5) + tfidf на numpy, косинус к тем же примерам. Ноль сетевых
  вызовов, ноль рублей, ~1 мс на запрос.

Оба возвращают top-k соседей, дальше работает общий гейт.

### Score и статус

Метка — победитель взвешенного голосования соседей (далёкий сосед голосует слабее ближнего).
Уверенность собирается из трёх сигналов:

| Сигнал | Что показывает | Вес |
|---|---|---|
| близость top-1 | насколько обращение вообще похоже на то, что мы видели | 0.4 |
| отрыв | лучший сосед победившей метки минус лучший сосед любой другой | 0.35 |
| согласие соседей | доля веса победителя среди top-k | 0.25 |

Статус `OK` — метка принимается. Статус `UNSURE` — идём на уровень 2, с явной причиной:

| Причина | Когда |
|---|---|
| `short_input` | текста меньше 12 символов — судить не по чему |
| `no_close_neighbor` | ближайший сосед ниже порога: обращение не похоже ни на что в банке |
| `fallback_label` | победил `other` — класс-помойка, уверенность в нём ничего не значит |
| `low_margin` | два класса впритык, отрыва нет |
| `low_score` | итоговая уверенность ниже порога accept |

## Уровень 2 — большая LLM

`openai/gpt-4.1`, строгий JSON `{"label", "confidence", "reason"}`, значения проверяются по enum, при
нарушении формата — один ремонтный вызов (переиспользован `call_stage` из Дня 9). Если формат не
сошёлся и после ремонта — берём метку micro-model, а не выдумываем ответ.

## Как запустить

```bash
curl -s -X POST http://localhost:8000/api/intent -H 'Content-Type: application/json' \
  -d '{"text":"Списали 9800 вместо 4900, верните лишнее","strategy":"micro_embed_first"}' | jq
```

В веб-чате:

```
/intent Списали 9800 вместо 4900, верните лишнее
/intent tfidf Не приходит код подтверждения при входе
/intent llm Не работает.
```

Прогон датасета и подбор порогов:

```bash
python docs/day10/run_eval.py --out run2.json && python docs/day10/report.py run2
python docs/day10/calibrate.py
```

## Результаты

32 обращения, каждое прогнано четырьмя стратегиями ([`runs/run2.md`](runs/run2.md)):

| Стратегия | Точность | Закрыла micro | Вызовов большой LLM | Стоимость | Latency avg / p50 / p95 |
|---|---|---|---|---|---|
| Сразу большая модель (базовая линия) | 87.5% (28/32) | 0% | **32** | 3.76 ₽ | 2686 / 2524 / 3636 мс |
| Micro-first, эмбеддинги | 81.2% (26/32) | **62.5%** | **12** | 1.40 ₽ | 1362 / 451 / 3358 мс |
| Micro-first, tfidf | 84.4% (27/32) | 53.1% | 15 | 1.76 ₽ | 1123 / **7** / 2781 мс |
| Только micro, без fallback | 75.0% (24/32) | 100% | **0** | 0 ₽ | 343 / 297 / 534 мс |

Ответ на вопрос дня: **micro-model отсекла 20 из 32 обращений (62.5%)**, вызовов большой модели
стало 12 вместо 32, счёт — 37% от базового, средняя задержка — вдвое меньше. Точность связки при
этом на 2 кейса ниже базовой линии.

Latency-профиль важнее среднего: у micro-first p50 = 451 мс (у tfidf — 7 мс), то есть половина
обращений отвечает почти мгновенно, а «дорогой хвост» p95 остаётся на уровне базовой линии — это
те кейсы, где мы сознательно доплатили за большую модель.

По группам видно, за что платим:

| Стратегия | Простые | Пограничные | Сложные |
|---|---|---|---|
| Базовая линия | 100% (12/12) | 66.7% (8/12) | 100% (8/8) |
| Micro-first, эмбеддинги | 100% (12/12) | 50.0% (6/12) | 100% (8/8) |
| Только micro | 100% (12/12) | 58.3% (7/12) | 62.5% (5/8) |

Простые обращения micro-model берёт без потерь — там она и должна работать (эскалировала лишь
25% простых). Сложные она отдаёт наверх заметно охотнее — 62.5% ушли на уровень 2, и в группе
получилось 8 из 8 верно: ровно то распределение работы, ради которого всё затевалось. Провал у стратегии
«только micro» на сложных (62.5%) — ровно та цена, которую платят за отказ от fallback: слишком
короткий вход, инъекция в тексте, обращение с двумя темами она не вытягивает.

### Почему кейсы уходили наверх

| Причина | Кейсов (эмбеддинги) |
|---|---|
| нет отрыва от второго класса (`low_margin`) | 7 |
| победил класс `other` (`fallback_label`) | 3 |
| score ниже порога (`low_score`) | 2 |

Решающий сигнал — не абсолютная близость, а **отрыв**. Обращения вроде «оплатил, но тариф не
переключился» одинаково похожи и на `billing`, и на `technical`; именно на них micro-model должна
поднимать руку, и она это делает.

### Калибровка порогов

Первый прогон [`runs/run1.md`](runs/run1.md) шёл на порогах, выставленных на глаз
(`accept 0.62 / sim_floor 0.45`): micro закрывала 46.9% и ошибалась на 2 принятых из 15. Дальше
[`calibrate.py`](calibrate.py) прогнал сетку `sim_floor × margin_min × accept` по уже посчитанным
соседям (без единого вызова LLM) и выбрал точку с максимумом покрытия при точности принятых не
ниже 90%. Итог: `accept 0.30 / sim_floor 0.30 / margin_min 0.01` — покрытие выросло с 46.9% до
62.5% при той же точности принятых решений (18 из 20).

Таблица калибровки в отчёте показывает неочевидное: **между accept 0.3 и 0.75 итоговая точность
связки не меняется вообще** (81.2%) — меняется только цена, от 12 вызовов до 24. Ужесточать порог
в этом диапазоне бессмысленно: кейсы, которые micro отдаёт наверх при более строгом пороге,
большая модель решает не лучше неё.

## Пределы и честные оговорки

- **Два кейса micro-model завалила уверенно** — `b05` (отзыв про удобный интерфейс, внутри которого
  спрятан баг с фильтром) и `b12` (архив не открывается — это `technical`, а банк тянет в
  `data_loss`). Score у обоих 0.75+, ни один порог их не отсекает, не убив половину покрытия. Это
  предел уровня 1 на таком банке: лечится примерами в банке, а не порогом.
- **Базовая линия сама нестабильна.** В run1 `llm_only` дала 90.6%, в run2 — 87.5% на тех же
  данных: на пограничных кейсах `gpt-4.1` при temperature 0.1 плавает между прогонами. Разница
  micro-first и базовой линии (2 кейса) — того же порядка, что и этот шум.
- **Правило «`other` всегда наверх» стоит 3 вызова из 32.** Все три раза micro-model была права.
  Оставил осознанно: `other` — свалка, и ошибка в ней дороже трёх вызовов.
- **Датасет 32 кейса** — этого хватает, чтобы увидеть порядок величин, но не хватает, чтобы
  всерьёз доверять разнице в один-два процента.
- **tfidf оказался не хуже эмбеддингов по точности связки** (84.4% против 81.2%) при нулевой цене
  уровня 1 — на маленьком банке из коротких шаблонных фраз символьные n-граммы работают на
  удивление хорошо. При росте банка и разнообразия формулировок ожидаемо развернётся в пользу
  эмбеддингов.
