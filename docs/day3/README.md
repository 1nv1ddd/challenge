# Day 3 — Testing (два уровня проверки)

**Дата:** 2026-07-22. Челлендж advance, неделя 8.

День про то, что «проверить» — это два разных занятия с разными инструментами:
**код-тесты** (быстро, точно, но видят только то, что вызвано напрямую) и
**smoke по живому UI** (медленно, зато проходит тот же путь, что пользователь).
Профиль на каждый уровень + две команды, которые их сшивают.

## Что сделано

| Артефакт | Файл | Прогон |
|---|---|---|
| Профиль `testgen` | [`.claude/agents/testgen.md`](../../.claude/agents/testgen.md) | ✅ 50 → **121** тест, зелёные |
| Профиль `smoke` | [`.claude/agents/smoke.md`](../../.claude/agents/smoke.md) | ✅ **5 из 5** сценариев PASS |
| Сценарии для smoke | [`smoke-scenarios.md`](smoke-scenarios.md) | 5 сценариев, 28 селекторов сверены с живой страницей |
| Команда `/verify` | [`.claude/commands/verify.md`](../../.claude/commands/verify.md) | полный цикл перед PR |
| Команда `/smoke-refresh` | [`.claude/commands/smoke-refresh.md`](../../.claude/commands/smoke-refresh.md) | обновить сценарии под изменившийся UI и перепрогнать |

Логи прогонов: [run-testgen.md](run-testgen.md), [run-smoke.md](run-smoke.md).
Скриншоты smoke: [`screenshots/`](screenshots/) — 34 файла.

Инфраструктура: Playwright MCP через [`.mcp.json`](../../.mcp.json) (`@playwright/mcp`, chromium);
Node ставился с нуля через brew — в системе его не было вообще.

## Результат

**`testgen`** сам провёл инвентаризацию (что есть в `app/` против того, что реально дёргается
в `tests/`), выбрал три цели с обоснованием и написал 71 новый тест. Весь сьют зелёный с первого
прогона; `git diff -- app/` чист — код приложения не тронут.
Перепроверено независимо: `Ran 121 tests ... OK`.

**`smoke`** прошёл 5 сценариев в реальном chromium, снял 34 скриншота, вердикт ставил
по DOM и кодам ответов, а не по картинке. Багов в приложении не нашёл — **зато нашёл шесть
дефектов в самих сценариях**, включая один принципиальный (см. ниже).

## Три вывода дня

### 1. Зелёный тест ничего не доказывает, пока не показан красным

Главное требование профиля `testgen`: для каждого файла внести **временную диверсию** в проверяемый
код, показать FAIL, вернуть как было. Без этого тест не считается написанным.

Насколько это не формальность, показала одна диверсия из одиннадцати. Профиль `review` (Day 2)
нашёл в `tests/test_branch_api.py:27` ассерт `assertNotIn("branch_id", r.json())`, который при
ответе 400 **тавтологически истинен**. `testgen` заменил его на проверку отсутствия побочного
эффекта — и доказал разницу, сымитировав правдоподобную регрессию «валидация после мутации»:
статус остаётся 400, тело ошибки по-прежнему без `branch_id`, **старый ассерт остался бы зелёным**,
пропустив реальную порчу данных. Новый краснеет: `Lists differ: ['main', 'branch-1'] != ['main']`.

### 2. Smoke-прогон окупился не поиском багов, а критикой сценариев

5 из 5 PASS — то есть по прямому назначению прогон не нашёл ничего. Ценность оказалась в другом:
сценарий S3 требовал негативной проверки «создать ветку без чекпойнта → убедиться, что не
создалась», но агент по network-логу увидел, что **фронт сам шлёт `POST /api/checkpoints` перед
созданием веток** — запроса без `checkpoint_id` из UI не бывает в принципе.

Отсюда вывод об уровнях: **этот контракт в принципе не защищается UI-тестом**, его может держать
только тест уровня API. Что прямо ушло во вход `testgen` — и там закрыто (`test_branch_api.py`,
1 → 4 теста). Пункт профиля «не менять сценарии под то, что работает — сказать отдельно
в *Замечания к сценариям*» сработал именно так, как задумывался: агент прошёл сценарий как
написано, поставил честный вердикт и отдельно сказал, что сценарий неверен.

### 3. Профили начали кормить друг друга

Ни один из двух прогонов сегодня не получал задание «с нуля»:

```
review (Day 2) ──► слабый ассерт в test_branch_api.py ──┐
                                                        ├──► вход для testgen
smoke (Day 3) ──► негативный путь недостижим из UI ─────┘
```

Это и есть execution loop из задания недели: main-агент не сам придумывает работу, а
маршрутизирует находки одного профиля во вход другого. Заодно вскрылось ограничение контрактов:
`testgen` по своему профилю **не имеет права** трогать существующие тесты, поэтому разрешение
править `test_branch_api.py` пришлось выдать во входе явным исключением. Жёсткий контракт — это
хорошо, но он требует, чтобы у вызывающего был способ его точечно ослабить.

## Хвосты

- **`testgen` нашёл 4 дефекта и не чинил их** (по контракту) — главный: `ValueError` из агента
  не мапится в HTTP, клиент получает **500 вместо 400** на `POST /api/branches`,
  `/api/checkpoints`, `/api/profiles`. Кандидат на вход профилю `bugfix`.
- Сценарии в `smoke-scenarios.md` **не обновлены** под 6 замечаний прогона — это ровно работа
  команды `/smoke-refresh`, оставлено как её будущий вход.
- `.claude/` лежит в [`.gitignore:12`](../../.gitignore) — профили и команды не попадают
  в репозиторий, хотя они и есть артефакт задания. Решить.
- После прогона smoke в `data/agent_memory.json` остались 3 тестовых диалога и профиль `Smoke QA`
  (UI удаления нет).
