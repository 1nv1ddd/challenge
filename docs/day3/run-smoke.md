## Что оказалось ценнее самих PASS

Все пять сценариев зелёные — то есть прогон **не нашёл ни одного бага в приложении**.
Зато нашёл шесть дефектов **в моих собственных сценариях**:

1. **S3, негативная проверка — недостижима из UI.** Сценарий требовал нажать «2 ветки»
   без чекпойнта и убедиться, что ветки не создались. Но фронт при этом клике **сам** сначала
   шлёт `POST /api/checkpoints`, и только потом `POST /api/branches` — запроса без `checkpoint_id`
   из интерфейса не бывает в принципе. Агент это увидел по network-логу, проверил контракт
   в обход UI (`curl` → `HTTP 400 {"detail":"Нужно поле checkpoint_id."}`) и предложил перенести
   проверку на уровень API-теста. **Это прямо повлияло на задание профилю `testgen`** — см.
   [run-testgen.md](run-testgen.md).
2. **S2 шаг 1 и S5 шаг 1 неполны:** блоки «Профиль» и «Инварианты» лежат в скрытом
   `#constraintsPanel`, нужен явный шаг «нажать *Ограничения*». Агент домыслил его сам.
3. **S3 шаг 2 не выполним как написан:** `#branchRow` имеет inline `display:none` и показывается
   только при `#contextStrategy = branching`. Кнопки в DOM есть, но некликабельны.
4. **S4 шаг 5 неточен:** `#mcpToolsSummary` — обычный `div`, а не `<summary>`; «раскрыть» — no-op.
5. **S4 шаг 2 неоднозначен:** «путь к серверу из `scripts/`» оставлял выбор агенту.
   Надо фиксировать путь и ожидаемое число тулзов.
6. **S1 не проверяет собственно стриминг:** ответ приходит за 1.5 с, ожидание «до 60 секунд»
   срабатывает мгновенно, промежуточное состояние стрима не проверяется.

## Наблюдение по механике профиля

Требование **«вердикт PASS/FAIL по DOM, а не по картинке»** оказалось рабочим: агент везде
подтверждал результат содержимым элементов и кодами ответов из network, а скриншоты использовал
как доказательство для человека. При обратном порядке (решать по скриншоту) шаг S3.6 почти
наверняка был бы засчитан как «ошибки не видно, значит негативный путь отработал» — тогда как
на деле ветки создавались, просто легитимно.
