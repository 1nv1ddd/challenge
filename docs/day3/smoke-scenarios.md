# Smoke-сценарии — AI Chat Hub

Пять пользовательских сценариев для профиля [`smoke`](../../.claude/agents/smoke.md).
Агент берёт их как есть и протыкивает живой UI через Playwright MCP.

**Базовый URL:** `http://localhost:8000/`
**Предусловие для всех:** dev-сервер поднят (`curl` на `/` отдаёт 200), `.env` с рабочим `ROUTERAI_API_KEY`.

В приложении **нет логина** — это локальный однопользовательский хаб, поэтому классический шаг
«логин» заменён на «открыть приложение и дождаться готовности интерфейса». Форма CRUD
(создать сущность → проверить, что появилась → удалить) сохранена в S2, S3 и S4.

---

## S1. Базовый чат: отправить сообщение и получить ответ

**Зачем:** главный путь продукта. Задевает `POST /api/chat` (SSE-стрим), выбор модели, рендер ответа.

1. Открыть `http://localhost:8000/`.
2. Дождаться, пока прогрузится список моделей в `#modelSelect` (в нём есть хотя бы один вариант).
3. Нажать `+ Новый чат` (`#newChatBtn`).
4. В поле ввода (`#userInput`) написать `Ответь ровно одним словом: тест` и отправить (`#pauseToggleBtn`).
5. Дождаться ответа ассистента в `#messages` (стрим SSE, ждать до 60 секунд).

**Ожидаемый результат:** в `#messages` появились два сообщения — пользовательское и ответ ассистента;
ответ непустой; в списке чатов слева (`#chatsList`) появился этот чат.

**Известный риск:** шаг 5 ходит в реальный LLM через RouterAI. Если ключ невалиден или сеть
недоступна — это FAIL инфраструктуры, а не регрессия UI; пометить именно так.

## S2. Профиль пользователя: создать → проверить → выбрать

**Зачем:** CRUD-сущность, задевает `GET/POST /api/profiles`.

1. Открыть приложение, раскрыть блок «Профиль пользователя».
2. Нажать `Новый профиль` (`#newProfileBtn`).
3. Заполнить: `#profileNameInput` = `Smoke QA`, `#profileStyleInput` = `сухо и по делу`,
   `#profileFormatInput` = `списком`, `#profileConstraintsInput` = `не больше 3 пунктов`.
4. Нажать `Сохранить профиль` (`#saveProfileBtn`).
5. Проверить, что профиль появился в `#profileSelect`.
6. Перезагрузить страницу и убедиться, что профиль всё ещё в списке (сохранился на сервере).

**Ожидаемый результат:** после шага 4 в `#profileSelect` есть опция `Smoke QA`, и она переживает
перезагрузку страницы.

**Уборка:** UI удаления профилей не предусмотрен — профиль `Smoke QA` останется. Это ожидаемо,
зафиксировать в разделе «Что осталось после прогона».

## S3. Ветки диалога: чекпойнт → создать ветку → переключиться

**Зачем:** прямая UI-регрессия на баг, починенный в Day 2 (`POST /api/branches` отдавал HTTP 200
при отсутствии `checkpoint_id`, и фронт рисовал успех там, где ветки не было).

1. Открыть приложение, создать новый чат и отправить любое короткое сообщение, дождаться ответа.
2. В блоке «Ветки» нажать `Checkpoint` (`#checkpointBtn`).
3. Нажать `2 ветки` (`#createBranchesBtn`).
4. Проверить `#branchSelect`: помимо `main` появились новые ветки.
5. Переключиться на созданную ветку и убедиться, что интерфейс переключился (`#branchRow` отражает выбор).

**Ожидаемый результат:** после шага 3 в `#branchSelect` больше одной опции; переключение работает.

**Отдельная проверка негативного пути (важно для этого сценария):** нажать `2 ветки` **до**
создания чекпойнта. Ожидается, что UI покажет ошибку либо ничего не создаст — и **не** покажет
ложный успех. Именно это ломалось до Day 2.

## S4. MCP-панель: подключить сервер → увидеть тулзы → отключить

**Зачем:** единственная полная CRUD-форма в UI (создать → проверить → удалить).
Задевает `POST /api/mcp/connect`, `GET /api/mcp/status`, `POST /api/mcp/disconnect`.

1. Открыть приложение, раскрыть MCP-панель (блок с `#mcpLocalBody`).
2. Заполнить: `#mcpServerId` = `smoke_git`, `#mcpServerName` = `Smoke Git`,
   `#mcpScriptPath` = путь к существующему серверу из `scripts/` (взять реальный файл из репозитория).
3. Нажать `Подключить` (`#mcpConnectBtn`).
4. Дождаться, пока `#mcpStatusBox` покажет подключение, а `#mcpToolsCount` — ненулевое число тулзов.
5. Раскрыть `#mcpToolsSummary` и убедиться, что в `#mcpToolsList` есть хотя бы один инструмент.
6. Нажать `Отключить все` (`#mcpDisconnectBtn`).
7. Проверить, что статус вернулся в «не подключено», а счётчик тулзов обнулился.

**Ожидаемый результат:** сервер подключается, тулзы видны, отключение полностью очищает состояние.

**Уборка:** выполняется шагом 6 внутри сценария.

## S5. Инварианты: сохранить и пережить перезагрузку

**Зачем:** проверка персистентности. Задевает `GET/POST /api/invariants` и запись в `data/`.

1. Открыть приложение, найти блок «Инварианты (хранятся вне диалога)».
2. В `#invariantsInput` ввести `проект: smoke-check`.
3. Нажать `Сохранить инварианты` (`#saveInvariantsBtn`).
4. Дождаться подтверждения в UI (строка «Инварианты: …» отражает новое значение).
5. Перезагрузить страницу.
6. Проверить, что инвариант на месте.
7. Очистить поле и сохранить пустое значение — вернуть исходное состояние.

**Ожидаемый результат:** инвариант сохраняется, переживает перезагрузку, снимается шагом 7.

**Уборка:** шаг 7. Если не сработал — сказать об этом, значение осталось в `data/agent_memory.json`.

## Как это гоняется

```
Прогони smoke-сценарии из docs/day3/smoke-scenarios.md
```

Профиль `smoke` пройдёт их по порядку, снимет скриншот на каждом шаге
в `docs/day3/screenshots/` и выдаст отчёт с PASS/FAIL и разбором падений.

Полный цикл (код-тесты + smoke + ревью одним прогоном) — команда `/verify`,
см. [`.claude/commands/verify.md`](../../.claude/commands/verify.md).
