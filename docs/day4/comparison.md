# Сравнение: локальная модель vs облачный ассистент

Таблица построена по **фактическому прогону** одной задачи (см. [runs/task.md](runs/task.md)),
а не по ожиданиям. Оценки по конвенциям — от независимого субагента `review`
(см. [runs/review-grading.md](runs/review-grading.md)), латентность/скорость локальной —
замеры Ollama.

## Условия прогона (одинаковые для обоих)

- Задача: добавить `GET /api/scheduler/jobs/{task_id}` (404 если нет), данные — из слоя стора.
- Правила проекта — в системном промпте (компактная версия, [rules-local.md](rules-local.md)).
- Контекст (`scheduler_routes.py` + факт про `scheduler_store.py`) вставлен в промпт обоим.
- Локальная: Vikhr-Nemo-12B (Q4_K_M) через Ollama, `temperature=0.2`, `num_ctx=8192`.
- Облачная: Claude, те же правила и контекст.

## Итог по конвенциям (8 пунктов CLAUDE.md, независимая оценка)

| # | Пункт правил | Локальная (Vikhr-12B) | Облачная (Claude) |
|---|---|---|---|
| 1 | reuse-first (Инвариант №1) | ❌ сырой доступ к БД в роутере | ✅ `get_job()` в сторе, роутер вызывает |
| 2 | нет `sqlite3.connect`/сырого SQL в роуте | ❌ импорт `_connect`, `SELECT` в роуте | ✅ доступ к БД только в сторе |
| 3 | параметризованный SQL | ✅ `WHERE task_id = ?` | ✅ `WHERE task_id = ?` |
| 4 | `from __future__ import annotations` | ❌ отсутствует | ✅ на месте |
| 5 | русский docstring модуля/функции | ❌ нет ни одного | ✅ модуль + обе функции |
| 6 | type-hints + аннотация возврата | ❌ нет `-> dict` | ✅ `-> dict` / `-> dict \| None` |
| 7 | `HTTPException` с русским detail | ❌ `"Job not found"` (англ.) | ✅ `f"Задача {task_id!r} не найдена"` |
| 8 | файл целиком, рабочие импорты | ❌ плейсхолдеры + `NameError` | ✅ целиком, импорты сходятся |
| | **Итого** | **2 / 8** | **8 / 8** |

**Запустится ли «скопировать-вставить»:** локальная — **нет** (`init_schema` не импортирован
→ `NameError`; плейсхолдеры `# ... остальной код` уничтожают существующие `/ping` и `/stream`).
Облачная — **да**, компилируется как есть.

## Операционные характеристики

| Параметр | Локальная (Vikhr-12B / Ollama) | Облачная (Claude) |
|---|---|---|
| Стоимость запроса | **0 ₽** (железо уже есть) | платно по токенам API |
| Латентность этой задачи | **30.7 с** (1081 ток. промпта → 166 ток. ответа) | секунды до первого токена |
| Скорость генерации | **14.8 ток/с** (M-серия, Q4) | заметно выше |
| Приватность кода | **код не покидает машину** | код уходит провайдеру |
| Работа офлайн | **да** | нет, нужна сеть |
| Контекст | 8192 ток. (задан); модель слабо держит длинный | большой, стабильно держит |
| Следование длинным правилам | теряет пункты → правила пришлось ужимать | держит полный CLAUDE.md |
| Autocomplete (FIM, tab) | **нет** — Vikhr не FIM-модель, нужна отдельная | есть |
| Reasoning на многофайловых задачах | слабый (ушёл в ловушку) | сильный |

## Что показал именно этот прогон

1. **Локальная 12B ловится ровно на том, ради чего задача и сделана** — сырой SQL и приватный
   `_connect` прямо в роутере. Функциональную форму (404 через `HTTPException`, параметризованный
   `?`) взяла, но 6 из 8 конвенций — мимо, и ответ нерабочий как есть.
2. **Формат ответа — отдельная проблема, не связанная с «умом».** Плейсхолдеры `# ... остальной код`
   вместо полного файла — это провал следования инструкции «верни файл целиком», который в IDE
   ломает apply-патч. Облачная вернула файл целиком.
3. **Правила пришлось ужать под 12B.** Полный CLAUDE.md (сотни строк) модель не держит — поэтому
   системный промпт локальной = короткая императивная выжимка. Это не косметика: длина правил —
   рычаг качества именно на слабой модели (обратно тому, что на сильной облачной, где длинный
   контекст безопасен).
