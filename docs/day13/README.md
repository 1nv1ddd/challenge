## Как устроен проход

```
запрос → rate limit → длина промпта → INPUT GUARD ─block→ отказ (модель не вызывается)
                                          │mask/pass
                                          ↓
                              модель (границы данных + канарейка)
                                          ↓
                                    OUTPUT GUARD ─block→ отказ
                                          │mask/pass
                                          ↓
                                    ответ + запись в аудит
```

Точка выхода одна: [`_finish()`](../../app/gateway/pipeline.py) — в аудит попадает **любой** исход,
включая отказ лимитера и ошибку провайдера. Поле `llm_called` отвечает на вопрос «сколько вызовов
модели мы не сделали»: в прогоне это 13 из 20 запросов.

## Input Guard

### Что ищем

| Группа | Виды | Как ловим |
|---|---|---|
| Ключи с префиксом | `openai_key` (`sk-`), `anthropic_key` (`sk-ant-`), `github_token` (`ghp_`/`gho_`/`github_pat_`), `aws_access_key` (`AKIA`/`ASIA`), `google_api_key` (`AIza`), `slack_token` (`xox…`) | regex по префиксу |
| Прочие учётные данные | `private_key` (PEM-заголовок), `jwt`, `connection_string`, `credential_assignment` | regex по формату или по слову-маркеру рядом (`password:`, `api_key=`) |
| ПДн | `card`, `email`, `phone` | regex; для карты — обязательная проверка Луна |

Порядок паттернов = приоритет: конкретный вид забирает участок текста раньше общего, поэтому
`sk-ant-…` попадает в лог как ключ Anthropic, а не как «что-то с `sk-`», а `api_key: sk-proj-…`
логируется одним точным видом, а не двумя пересекающимися.

### Три представления текста

Секрет ищется не только «как прислали»:

| Вариант | Что делает | Пример из корпуса | Можно ли маскировать |
|---|---|---|---|
| `direct` | ищет в исходном тексте | `openai-key` | да, по точным границам |
| `base64` | декодирует base64-блобы и прогоняет по ним те же детекторы | `base64-secret` | да, маской накрывается весь блоб |
| `joined` | склеивает разорванные литералы (`"sk-" + "proj-abc"`) и вырезает zero-width символы | `split-secret`, `zero-width-key` | **нет** |

Ключевое следствие: находка варианта `joined` **всегда** ведёт к блокировке, даже в режиме `mask`.
Границ секрета в исходном тексте не существует — он собран из кусков, и маскировать нечего. Это не
недоделка, а честная граница подхода: там, где нельзя вырезать точно, единственный безопасный
ответ — отказ.

### Блокировка против маскирования

Задание требует обе стратегии, и они не взаимозаменяемы — поэтому режим выбирается запросом:

| Режим | Поведение | Когда нужен |
|---|---|---|
| `hybrid` (по умолчанию) | учётные данные → блок, ПДн → маска | рабочий режим: ключ утёк = его надо отзывать, а не прятать; а вот почта клиента запрос ломать не должна |
| `mask` | всё маскируется, запрос идёт дальше | когда важнее не мешать пользователю |
| `block` | любая находка → отказ | строгий контур; цена видна на кейсе `email-block-mode` — отказ из-за обычной почты |
| `off` | guard выключен | база для сравнения |

Почему по умолчанию именно `hybrid`: маскирование скрывает ключ от модели, но **не отменяет самого
факта утечки** — ключ уже прошёл через буфер обмена, историю чата и логи браузера. Замаскировать и
промолчать — значит скрыть инцидент. Поэтому на учётных данных шлюз отвечает отказом с текстом
«ключ нужно отозвать», а не тихим `[REDACTED_API_KEY]`.

## Output Guard

Проверяется ответ модели до выдачи пользователю:

| Находка | Что ловит | Реакция |
|---|---|---|
| `secret` | те же детекторы, что на входе: модель галлюцинирует ключи и повторяет то, что видела | маска |
| `prompt_leak` | канарейка `SECURITY_CANARY` в ответе, дословный кусок системного промпта (n-gram из Дня 11) или обороты вида «вот мои инструкции» | **блок целиком** |
| `suspicious_url` | хост вне allowlist | маска |
| `dangerous_command` | `rm -rf /`, `curl … \| sh`, `base64 -d … \| bash`, `chmod 777`, `dd of=/dev/…`, fork-бомба, `iex(…http…)`, затирание истории | **блок целиком** |

Детекторы секретов, канарейки и разбора ссылок переиспользованы, а не написаны заново:
`scan_text()` из input guard, `canary_leak()`/`prompt_leak()` из [`app/security/verdict.py`](../../app/security/verdict.py),
`find_urls()`/`host_allowed()` из [`app/indirect/guard.py`](../../app/indirect/guard.py) (Дни 11–12).

## Тест-кейсы: что поймали, что пропустили

Полная таблица — [`runs/run1.md`](runs/run1.md). Коротко: **20 кейсов, 18 совпало с ожиданием, 2 пропуска**.

| Кейс | Итог |
|---|---|
| чистый промпт | ✅ проходит без изменений |
| AWS-ключ, ключи OpenAI/Anthropic/GitHub/Google | ✅ блок |
| номер карты (Луна валиден) | ✅ маска |
| номер заказа из 16 цифр (Луна не сходится) | ✅ не трогаем — контроль ложных срабатываний |
| почта + телефон | ✅ маска, запрос остаётся рабочим |
| секрет в base64 | ✅ блок, вариант `base64` |
| секрет, разбитый на части `"sk-" + "proj-abc"` | ✅ блок, вариант `joined` |
| ключ с zero-width символами внутри | ✅ блок |
| JWT, PEM-ключ, `password:`, строка подключения | ✅ блок |
| ключ задом наперёд | ❌ **пропуск** |
| ключ в hex | ❌ **пропуск** |

Оба пропуска зафиксированы в тесте явным списком: новый пропуск роняет прогон, а известные —
задокументированы. Причина, по которой они не закрыты: обратимых кодировок бесконечно много
(hex, rot13, urlsafe-base64, «через пробел», «через точку»), каждая новая — это ещё один полный
проход по тексту и ещё один источник ложных срабатываний. Регулярки на входе — сито, а не стена;
серьёзный контур строится вокруг ротации ключей и DLP, а не вокруг угадывания кодировок.

## Rate limiting и cost tracking

- **Лимит:** 10 запросов в минуту на IP, скользящее окно ([`ratelimit.py`](../../app/gateway/ratelimit.py)).
  Заблокированный guard'ом запрос слот тоже занимает — иначе перебор секретов был бы для атакующего
  бесплатным. Состояние живёт в процессе: при нескольких воркерах лимит умножается на их число,
  для прода это выносится в Redis.
- **IP за nginx** берётся из `X-Forwarded-For`; заголовку можно верить только потому, что снаружи
  приложение доступно исключительно через свой nginx.
- **Стоимость** считается на каждом запросе по прайсу конкретной модели
  ([`routing/pricing.py`](../../app/routing/pricing.py), День 8). Если провайдер не вернул `usage`,
  токены оцениваются по длине текста и запись помечается `estimated: true` — «неизвестно» в
  биллинге хуже, чем «примерно».

## Аудит

`data/gateway_audit.jsonl`, append-only, одна строка на запрос: время, `request_id`, IP, модель,
режим, статус, находки обоих guard'ов, маскированный промпт, ответ, токены, стоимость, время.

**Сырого секрета в логе нет никогда** — ни при блокировке, ни при маскировании. Остаются вид,
шесть первых символов и sha256-префикс. Это проверяется тестом `test_record_has_masked_prompt_only`
и ещё раз — при выгрузке [`runs/audit-sample.jsonl`](runs/audit-sample.jsonl).

Побочная польза от `digest`: десять попыток отправить один и тот же токен видны в логе как один
хэш, а не как десять разных утечек.

## API

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/api/gateway/chat` | прокси-вызов; 400 при блокировке входа, 429 при лимите |
| `GET` | `/api/gateway/audit?limit=50` | последние записи аудита и сводка |
| `GET` | `/api/gateway/cases?ids=` | корпус кейсов и его офлайн-прогон |
| `GET` | `/api/gateway/config` | режимы, лимиты, виды секретов, плейсхолдеры |

```bash
curl -s -X POST http://localhost:8000/api/gateway/chat \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"Мой ключ sk-proj-abc123XYZ456def789 отдаёт 401","mode":"mask"}'
```

В веб-чате то же самое: `/gateway mask мой ключ sk-proj-abc123XYZ456def789 отдаёт 401`,
`/gateway selftest`, `/gateway audit`.

## Что оказалось неочевидным

1. **Маскирование — не замена блокировке, а другой инструмент.** Для ПДн маска идеальна: запрос
   остаётся осмысленным. Для ключа маска — способ скрыть инцидент от службы безопасности.
2. **Не всё, что нашли, можно замаскировать.** Секрет, собранный из кусков, не имеет границ в
   исходном тексте. Либо блокировать, либо переписывать промпт целиком — третьего нет.
3. **Первый слой защиты — системный промпт, а не guard.** В живом прогоне модель сама написала
   `[REDACTED_API_KEY]` вместо примера ключа: до output guard дело не дошло.
4. **Allowlist доменов даёт ложные срабатывания сразу.** Легитимная ссылка на `12factor.net` была
   замаскирована. Строгий список безопасен, но для реального шлюза нужен либо ведомый список
   компании, либо репутационная проверка.
5. **Живой прогон нашёл дыру быстрее корпуса.** Строку подключения с паролем внутри добавил в
   детекторы не тест, а обычный ответ модели про `.env`-файл.
