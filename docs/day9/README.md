# Day 9 — Декомпозиция инференса

**Дата:** 2026-07-31. Челлендж advance, неделя 8.

Задача: входящее письмо-заявка на металлопрокат превращается в решение, которое уходит клиенту.
Одним запросом это делается плохо — в одном ответе модель должна одновременно вытащить восемь
полей из шумного текста, привести их к канону (тонны → килограммы, «300к» → 300000, «через две
недели» → дата, город → регион), применить политику приёма из семи правил с арифметикой по
срокам и написать письмо. Ошибка на любом шаге ломает всё остальное, и понять, где именно
сломалось, по одному ответу невозможно.

## Задача

**Вход:** свободное письмо клиента + дата обращения (от неё считаются относительные сроки).

**Что надо получить:**

1. восемь нормализованных полей — `company`, `product`, `qty_kg`, `budget_rub`, `deadline`,
   `region`, `contact`, `payment`;
2. решение `accept` / `clarify` / `reject` с кодом причины;
3. письмо клиенту.

**Политика приёма** (единый текст для всех вариантов, собирается из констант в
[`policy.py`](../../app/staged/policy.py), порядок проверки — часть политики):

| № | Условие | Решение |
|---|---|---|
| 1 | `product = other` (нет в каталоге) | `reject` / `product_not_in_catalog` |
| 2 | `region = abroad` | `reject` / `region_not_served` |
| 3 | `budget_rub` < 100 000 ₽ | `reject` / `below_min_order` |
| 4 | любое обязательное поле = `unknown` | `clarify` / `missing_fields` |
| 5 | до `deadline` меньше срока поставки по региону | `reject` / `deadline_unrealistic` |
| 6 | `payment = postpay_60` | `clarify` / `payment_terms_review` |
| 7 | иначе | `accept` / `ok` |

Срок поставки по регионам: Москва 3 дня, Санкт-Петербург 4, Урал 7, Юг 7, Сибирь 10.

## Вариант A — monolithic

Один запрос, один ответ: правила нормализации + политика + требования к письму в системном
промпте, письмо клиента — в пользовательском. Модель обязана вернуть три блока подряд:
восемь строк полей, три строки `DECISION` / `REASON` / `MISSING`, тему и текст письма.

Прогоняется на двух моделях — сильной (`openai/gpt-4.1`) и дешёвой
(`google/gemma-3n-e4b-it`), чтобы отделить «задача сложная» от «модель слабая».

## Вариант B — multi-stage

```
письмо + дата обращения
  │
  ├─ этап 1: нормализация входа        openai/gpt-4o-mini
  │     письмо → 8 строк «ключ: значение», enum-ы, даты ISO, числа целыми
  │     решения не принимает, письмо не пишет
  │
  ├─ этап 2: решение по политике       google/gemma-3n-e4b-it
  │     вход — 8 строк, а не письмо
  │     выход — ровно 3 строки: DECISION / REASON / MISSING (строгий enum)
  │
  └─ этап 3: формирование результата   google/gemma-3n-e4b-it
        вход — поля + принятое решение
        выход — SUBJECT + текст письма не длиннее 70 слов
```

Каждый этап — короткий запрос со своей моделью и своим строгим форматом. Разбор ответа
делают парсеры в [`parse.py`](../../app/staged/parse.py): enum вне списка, дата не в ISO,
телефон не в `+7XXXXXXXXXX`, число с единицами измерения — всё это ошибка формата, а не
«ну почти правильно». При ошибке этап повторяется один раз с показом модели её же ответа и
конкретной претензии.

### Третий режим: этап 2 без модели

Как только вход нормализован, политика перестаёт нуждаться в модели: семь правил по восьми
полям — это код. Режим `staged_rules` оставляет модели этапы 1 и 3, а решение считает
[`decide_by_rules()`](../../app/staged/policy.py) — та же политика, что лежит в промпте.
Это не обход задания, а его следствие: декомпозиция показывает, какой из этапов вообще не
требовал LLM. Тот же код работает запасным путём в обычном режиме `staged` — если этап 2
сорвал формат, решение всё равно будет принято по уже извлечённым полям.

## Как проверить руками

Дев-сервер: `uvicorn app.main:app --reload --port 8000`, дальше — веб-чат
[localhost:8000](http://localhost:8000/). Дату обращения полезно фиксировать через `today=`,
иначе сроки считаются от сегодняшнего дня.

```
/intake today=2026-07-30 ООО Ромашка. Нужны трубы 1,5 т, Москва, до 15 августа, бюджет 400к, предоплата. +7 999 123-45-67
```

```
/intake mono today=2026-07-30 Здравствуйте, интересуют трубы. Объёмы уточним позже. Доставка в Омск. Бюджет до 300 тысяч. info@omsk-stroy.ru
```

```
/intake rules today=2026-07-30 ООО Быстро. Срочно нужны фитинги, 200 кг, Москва, нужно завтра! Бюджет 150к, предоплата. +7 916 123-45-67
```

В карточке под ответом видно нормализованные поля, решение с кодом причины и таблицу этапов —
модель, число вызовов, был ли ремонт формата, время и цена каждого этапа.

То же через API:

```bash
curl -s -X POST http://localhost:8000/api/intake -H 'Content-Type: application/json' -d '{"letter":"ООО Ромашка. Нужны трубы 1,5 т, Москва, до 15 августа, бюджет 400к, предоплата. +7 999 123-45-67","mode":"staged","today":"2026-07-30"}'
```

## Замеры

Прогон: `python docs/day9/run_eval.py --out run1.json`, отчёт: `python docs/day9/report.py run1`.
Датасет — 24 письма: чистые, шумные формулировки, решения по условиям и ловушки (номер заказа
и ИНН рядом с объёмом, город вне обслуживаемых регионов, диапазон бюджета, заявка внутри
жалобы). Перед прогоном скрипт проверяет сам датасет: политика, применённая кодом к эталонным
полям, должна давать эталонное решение — иначе прогон не стартует.

### Прогон 1 — извлечение на `gpt-4o-mini` ([runs/run1.md](runs/run1.md))

| Метрика | A. Монолит, `gpt-4.1` | A. Монолит, `gemma-3n` | B. Этапы, решение моделью | B. Этапы, решение кодом |
|---|---|---|---|---|
| **Вердикт верен** | 19/24 (79%) | 11/24 (46%) | 8/24 (33%) | **24/24 (100%)** |
| Полей верно | 190/192 | 182/192 | 189/192 | 189/192 |
| Вызовов LLM | 24 | 24 | 74 | 50 |
| Стоимость прогона | 9.02 ₽ | 0.25 ₽ | 0.56 ₽ | **0.48 ₽** |
| Latency p50 | 2.6 с | 6.0 с | 7.4 с | 6.6 с |

**Декомпозиция сама по себе проиграла монолиту: 8/24 против 19/24.** Дешёвая модель на этапе 2
разваливается даже на идеально нормализованном входе — 13 из 16 её ошибок это один и тот же
ответ `below_min_order`, то есть модель не сравнивает бюджет с порогом, а цепляется за первое
правило, где встретилось число. Короткий вход и строгий enum-формат от этого не спасают.

Зато декомпозиция показала, **где** именно ломается задача. Извлечение полей — не проблема ни
для кого: 190/192 у `gpt-4.1` и 189/192 у `gpt-4o-mini`, который в пять раз дешевле. Всё
качество решает этап 2, и даже сильная модель проваливает его на своих же правильно извлечённых
полях — все 5 ошибок `gpt-4.1` это применение политики, а не чтение письма:

| Кейс | Эталон | `gpt-4.1` ответил | Что не сошлось |
|---|---|---|---|
| c08 | `reject` / `deadline_unrealistic` | `accept` / `ok` | «до конца месяца» = завтра, а юг — 7 дней |
| c13 | `reject` / `deadline_unrealistic` | `accept` / `ok` | 7 дней против сибирских 10 |
| c19 | `reject` / `deadline_unrealistic` | `accept` / `ok` | 6 дней против сибирских 10 |
| c12 | `accept` / `ok` | `reject` / `deadline_unrealistic` | ровно граница SLA: 3 дня при норме 3 |
| c15 | `reject` / `below_min_order` | `clarify` / `missing_fields` | порядок правил: бюджет проверяется раньше уточнения |

Все пять — арифметика по датам и порядок правил, то есть ровно то, что модели делать не нужно.
Как только этап 2 заменён кодом (`staged_rules`), вердикт становится **24/24 при 5.3% стоимости
монолита на сильной модели**.

### Прогон 2 — извлечение тоже на `gemma-3n` ([runs/run2.md](runs/run2.md))

Второй прогон отвечает на следующий вопрос: если этап 2 вообще не нужен модели, можно ли
удешевить и этап 1? Конфигурация та же, но нормализацию делает `gemma-3n-e4b-it` вместо
`gpt-4o-mini` — вся цепочка на дешёвой модели.

| Метрика | Этапы + код, извлечение `gpt-4o-mini` | Этапы + код, извлечение `gemma-3n` |
|---|---|---|
| Вердикт верен | 24/24 | 20/24 |
| Полей верно | 189/192 | 183/192 |
| Стоимость прогона | 0.48 ₽ | 0.23 ₽ |

Экономия вдвое стоит четырёх вердиктов, и ошибки именно те, которых нельзя допускать:

- **c05** — Алматы распознан как регион `south` вместо `abroad`, заявка из-за границы принята
  вместо отказа;
- **c23** — Казань, города нет в обслуживаемых группах, но модель вписала `ural` вместо
  `unknown`, то есть выдумала регион вместо уточнения;
- **c02**, **c24** — почтовый адрес в подписи не извлечён (`contact: unknown`), заявка ушла на
  уточнение вместо приёма;
- **c08** — в поле `contact` подставлен телефон, которого в письме нет вообще.

Отдельно: `gpt-4.1` в обоих прогонах ошибается **на одних и тех же пяти письмах**, а `gemma-3n`
в монолите — на одних и тех же тринадцати. Это не разброс температуры, а систематический провал
на применении правил.

### Итог по этапам

| Этап | Кому отдавать | Почему |
|---|---|---|
| 1. Нормализация | модели среднего тира (`gpt-4o-mini`) | 189/192 против 183/192 у дешёвой; экономия вдвое стоит принятой заграничной заявки |
| 2. Решение по политике | коду | и дешёвая (8/24), и сильная (19/24) модель проваливают арифметику по срокам и порядок правил; код — 24/24 |
| 3. Письмо клиенту | дешёвой модели | формат держит, но содержание надо проверять (см. ограничения) |


## Выводы дня

1. **Декомпозиция сама по себе ничего не улучшает.** Три коротких запроса вместо одного большого
   дали 8/24 против 19/24 — потому что «короткий и дешёвый» этап всё равно упирается в
   способности модели, которой его отдали. Строгий enum-формат и вход в восемь строк не делают
   слабую модель способной сравнить два числа.
2. **Ценность декомпозиции — в наблюдаемости.** Разложив задачу, видно вклад каждого этапа:
   извлечение почти идеально у всех, а весь провал сидит в применении правил. По одному
   монолитному ответу этого не увидеть — там ошибка приходит уже смешанной с результатом.
3. **Лучший этап — тот, который удалось не отдавать модели.** Как только вход нормализован,
   политика становится обычным кодом: 24/24 при 5.3% цены монолита. Это и есть настоящий
   выигрыш декомпозиции — не «разбили на три запроса», а «нашли, какой запрос лишний».
4. **Сильная модель не спасает от условной логики.** `gpt-4.1` ошибается ровно там, где надо
   вычесть даты и сравнить с таблицей SLA, и делает это стабильно — одни и те же 5 писем в двух
   прогонах.
5. **У цепочки есть частичный результат, у монолита — нет.** Сорванный формат на этапе 2 не
   уносит извлечённые поля: политика применяется кодом по ним же (`rules_fallback`, сработало
   2 раза за прогон 1). У монолита ошибка формата уносит весь ответ целиком.

## Ограничения

- **Датасет синтетический**: 24 письма, написанные под эту же политику. Эталонные решения
  проверяются политикой в коде — это измеряет применение правил, а не поведение на реальном
  потоке заявок.
- **Конвенции нормализации — соглашение, а не истина.** «До конца месяца», «в начале августа»,
  «в течение недели» разложены в даты правилами из промпта. На реальных письмах такие фразы
  спорны, и часть «ошибок» модели была бы спором о трактовке.
- **Качество письма не измеряется** — скрипт проверяет только формат и лимит длины. Ручная
  сверка прогона 1 показала: в 2 письмах из 24 этап 3 на `gemma-3n` подставил чужой товар
  («заявка на поставку арматуры» вместо труб), а один раз протащил в тему сырой enum
  `"wire_rope"`. Для продакшена этап 3 нужен либо на модели получше, либо на шаблонах.
- **100% у `staged_rules` — свойство задачи, а не метода.** Политика формализуема целиком. Как
  только правило станет нечётким («клиент выглядит ненадёжным»), кодом его не закрыть, и этап 2
  вернётся модели вместе со всеми своими ошибками.
- **Ремонт формата — одна попытка** (`INTAKE_MAX_REPAIRS`). При сорванном этапе 1 цепочка
  дальше не идёт: разбирать нечего, заявка уходит на уточнение.
- **Цены** — прайс RouterAI на дату прогона, `ROUTING_MODEL_PRICES_RUB` в
  [`agent_constants.py`](../../app/agent_constants.py).
