# Сравнение: облако (Run 1) vs локальная модель на пуле Day 5

**Дата:** 2026-07-24. Локальная модель — `Vikhr-Nemo-12B-Instruct-R` (Q4_K_M) через Ollama 0.21.0,
`temperature=0.2`, `num_ctx=8192`, системный промпт — сжатые правила Day 4
([`rules-local.snapshot.md`](rules-local.snapshot.md)). Прогон: [`local_run.py`](local_run.py),
сырые выводы — [`runs/local/`](runs/local/).

## Методика (и её честные границы)

Локальная модель — не агент: у неё нет инструментов, чтобы исследовать репозиторий, прогонять
тесты, коммитить. Поэтому, как в Day 4, ей давали **тот же текст задачи + необходимый контекст кода**
и просили один код-блок (single-shot). Облако (Run 1) те же задачи делало **автономно в execution-loop**
(исследование → тест → доказательство «красным» → прогон всего сьюта → коммит). Значит:
- **время не сравнимо в лоб**: локалка ~21 с/задача на генерацию с поданным контекстом; облако
  ~112 с/задача на полный автономный цикл. Быстрее ≠ дешевле по итогу.
- **сравнима — пригодность вывода**: скомпилируется ли, пройдёт ли критерий «сделано», нет ли
  скрытого дефекта, соблюдены ли конвенции. Это и мерили, проверяя каждый вывод фактически
  (применил в scratch-копии worktree, прогнал сьют/TestClient).

Взяты 4 задачи из пула — микс типов и разные «ловушки конвенций»: T06 (reuse-first),
T04 (payload-паттерн), T14 (Инвариант №1 + type-hints), T02 (unittest, не pytest).

## Вывод

Локальная 12B на **этом** микро-пуле выдаёт **синтаксически рабочий код в 4/4**, но:
- строгий критерий задачи выполнен в **3/4** (одна фича с неверной семантикой);
- **половина** «зелёных» несёт скрытый дефект или нарушение конвенции, которое проходит имеющиеся
  тесты — самый опасный класс (T04: 500 на не-объектном теле; T14: `typing.Dict`);
- reuse-first частично усвоен (T06 переиспользовал `list_jobs()` вместо сырого SQL — плюс),
  но целостность файла и граничные случаи (пустой список, не-объектное тело) теряются.

Это согласуется с Day 4 (локалка 2/8 по конвенциям): **локальной модели хватает на механические,
хорошо ограниченные правки с поданным контекстом, но не на автономный execution-loop** — нет
инструментов для самопроверки, а без прогона тестов её скрытые дефекты (500/404) уехали бы в коммит.
Облачный ассистент те же 4 задачи в Run 1 сделал чисто и с доказательством «красным», потому что
**цикл, а не только генерация**: исследовал контекст сам, писал регресс, гонял весь сьют.

## Что это говорит про профили/правила

- Правило **«верни один код-блок без прозы»** локалка нарушила (T02) — в IDE-режиме это ломает
  auto-apply. Кандидат в усиление `rules-local`.
- Отсутствие **guard/граничных случаев** (T04, T06) — локалке нужно явно прописать в правилах
  «сохраняй существующие проверки; list-эндпоинт на пустоте — 200 с `[]`, не 404».
- Главный системный вывод: ценность облачного профиля не в «умнее генерирует», а в **обвязке цикла**
  (verify + red-before + весь сьют). Локальную модель имеет смысл ставить только за такой же
  обвязкой, иначе её скрытые дефекты не ловятся.
