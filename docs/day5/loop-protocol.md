# Loop protocol — фиксированный протокол оркестрации Run 1

> Этот файл **заморожен до старта прогона**. В этом и смысл автономности:
> оркестратор не переписывает промпт под конкретную задачу и не подсказывает
> профилю между задачами. Меняются профили/правила — только между прогонами
> (Run 1 → усиление → Run 2), не внутри прогона.

## Роли

- **Оркестратор** — main-агент. Читает бэклог, выбирает профиль по типу, диспатчит,
  проверяет, коммитит/откатывает, пишет лог. Не чинит результат руками.
- **Профили** — субагенты `.claude/agents/*.md` (Days 1–2). Получают задачу, работают
  автономно, возвращают отчёт + дифф.

## Изоляция

- Всё Run 1 — в git worktree `day5-run1` от `base_sha` (`docs/day5/backlog.json`).
- Тесты — питоном основного venv: `/Users/1nv1d/challenge/.venv/bin/python -m unittest discover -s tests`, `cwd` = worktree.
- `main` не трогается; в конце в `main:docs/day5/runs/` харвестятся только логи/метрики.

## Роутинг профиля (ассистент «сам выбирает профиль»)

Детерминированно по полю `type` задачи (`meta.profile_routing` в backlog.json):

| type | кто исполняет |
|------|---------------|
| `bug` | субагент **bugfix** |
| `test` | субагент **testgen** |
| `research` | субагент **research** |
| `refactor` / `feature` / `docs` | **оркестратор inline** по CLAUDE.md (для них выделенного профиля нет) |

## Цикл (для каждой задачи по порядку)

1. Взять первую `pending` из backlog.json.
2. Засечь `t_start`.
3. **Диспатч** по роутингу. Субагенту передаются: id, title, detail, критерий done,
   абсолютный путь worktree как рабочий корень. Человек не вмешивается.
4. **Verify** (единый для всех):
   - весь сьют `unittest discover -s tests` из worktree — зелёный;
   - критерий `done` задачи выполнен (проверяется оркестратором по факту: grep/TestClient/curl).
5. Засечь `t_end`.
6. **Исход:**
   - **Verify зелёный** → `git add -A && git commit -m "Day 5 (run1) TNN: <title>"` в worktree,
     `gh issue close <n> -c "run1: done"`, статус `done`, `first_try=true`.
   - **Verify красный** (после возврата профиля) → **не чинить руками**: статус `failed`,
     проставить `reason` (категории ниже), `git restore -SW . && git clean -fd` — следующая
     задача стартует из last-good коммита. Issue остаётся открытым.
   - **Отказ по контракту** (bugfix отказался выдумывать невоспроизводимый баг и т.п.) →
     статус `refused` — это валидный сигнал, не провал пула; verify не запускается.
7. Дописать строку в `runs/run1.jsonl`.
8. Следующая задача. **Проходим весь пул** (18 задач) — чтобы получить и streak, и first-try %.

## Категории причины слома (`reason`)

- `no-context` — не понял контекст задачи/проекта, сделал не то.
- `broken-code` — сгенерировал нерабочий/непроходящий код.
- `loop` — зациклился / не сошёлся.
- `convention-violation` — работает, но нарушает CLAUDE.md так, что verify по критерию не проходит.
- `wrong-profile` — тип→профиль дал неподходящего исполнителя.
- `regression` — сломал ранее зелёные тесты.

## Метрики (`metrics.py` по `runs/run1.jsonl`)

- **streak** — длина ведущей серии `done` до первого `failed`/`refused` («сколько подряд без паузы»).
- **точка слома** — первый не-`done` + его `reason`.
- **avg time** — среднее `t_end − t_start` по всем задачам.
- **first-try %** — доля задач с `first_try=true` от всех.
- **done/failed/refused** — разбивка исходов.

## Строка лога (`run1.jsonl`, одна на задачу)

